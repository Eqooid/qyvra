# Brainless — Agent Instructions

## Required context

Before changing code, read `README.md` and the relevant files under `docs/`:

- `docs/specification.md` for product scope and acceptance criteria.
- `docs/architecture.md` for system boundaries and infrastructure rules.
- `docs/database.md` for storage ownership, entities, and constraints.
- `docs/api.md` for HTTP contracts and endpoints.
- `docs/roadmap.md` for delivery phases and current scope.

Also read the nearest nested `AGENTS.md` for the application being changed.

## Workspace layout

- `apps/web`: Next.js frontend using TypeScript, Tailwind CSS, and shadcn/ui.
- `apps/api`: NestJS REST API.
- `apps/*-worker`: asynchronous workers.
- `packages/database`: Prisma schema, migrations, and database client.
- `packages/contracts`: provider-neutral shared contracts.
- `infrastructure`: Docker, Nginx, RabbitMQ, and service configuration.

## Architecture rules

- Build a modular monolith with independently runnable workers.
- PostgreSQL is the system of record; Qdrant and Elasticsearch are rebuildable indexes.
- Store uploaded binaries through a storage abstraction, never in PostgreSQL or RabbitMQ.
- RabbitMQ messages contain identifiers and storage references, not files, extracted documents, or vectors.
- Background jobs must be idempotent, resumable, retryable, and observable.
- Keep domain and application logic independent from infrastructure SDKs.
- Keep text-generation and embedding providers independently configurable.
- Support Ollama locally and OpenAI as an optional adapter.
- Never compare vectors generated by different embedding profiles.
- Apply the authenticated `userId` filter to every Qdrant and Elasticsearch query.

## Authentication and security

- Initially use PostgreSQL-backed local authentication with Argon2id.
- Keep the stable internal `users.id` as the ownership key.
- Support future Keycloak identities through `provider + issuer + subject`.
- Never use email as the permanent external identity identifier.
- Derive ownership from trusted authentication context, not a request-provided `userId`.
- Never commit or log credentials, API keys, token values, password hashes, or session hashes.
- Validate request DTOs, environment variables, file signatures, MIME types, sizes, and ownership.

## Engineering workflow

1. Inspect the repository and relevant documentation before editing.
2. State the files and behavior that will change.
3. Implement only the requested roadmap phase or feature.
4. Preserve unrelated user changes.
5. Add or update tests for completed behavior.
6. Run formatting, linting, type checking, tests, and relevant production builds.
7. Update documentation when contracts or architectural decisions change.
8. Report verification results and remaining limitations.

Use strict TypeScript, avoid unjustified `any`, do not silently swallow errors, and do not leave placeholder behavior in a feature described as complete.
