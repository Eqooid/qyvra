## Implemented candidate scope

- Owned PostgreSQL generation/revision/publication state, explicit v3 contracts,
  transactional enrollment/outbox and independently runnable search workers.
- Private authenticated Elasticsearch adapter and optional deployment; deterministic
  model-independent PDF extraction/segments and verified lexical publication.
- Authenticated keyword API, existing semantic retrieval and document RRF60 hybrid
  search, SQL authorization, bounded fixed windows and explicit failures.
- Safe scalar-range highlights, authorized metadata autocomplete and retained exact
  canonical text sources. `/search` uses existing Next.js/shadcn/AuthApi patterns.
- Operator-role CLI for bounded resumable backfill, shadow generation rebuilding,
  verified SQL cutover, reconciliation and exact-manifest cleanup.

No OCR, new embedding models, agent framework, generated search answers, new vector
store, public search-engine access or historical binary PDF viewer. Existing RAG
and provider interfaces remain in place; real Phase 5 provider integration remains
an acceptance gate. Keyword/extraction do not need OpenAI, Ollama or Qwen.

## Architecture and database changes

PostgreSQL remains authoritative; ES/Qdrant are rebuildable indexes and Redis is
disposable. Preserve all original file/storage/database volumes. The three new
migrations follow the existing fifteen:

1. `20261013010000_search_persistence`: generation/state/projection/change
   persistence and nullable processing-job lineage; seeds no work.
2. `20261014010000_search_lifecycle_fencing`: lifecycle/fanout/processing guards.
3. `20261015010000_search_maintenance`: durable operation leases/checkpoints and
   `(fingerprint, generation)` uniqueness for same-profile physical rebuilds.

Old migrations are unchanged. The populated T09-to-T10 upgrade test preserved the
entire immutable document-version row; fresh 18-migration deployment passed locally.
This is not production migration certification or an automatic downgrade guarantee.

## Upgrade from v1.3.1

1. Back up PostgreSQL and original file storage and confirm restorable matching
   binaries/configuration. Inventory runtime versions, existing volumes and data.
2. Keep search enrollment, keyword and hybrid flags off during coordinated rollout.
   Apply additive migrations with existing tooling in a separately authorized
   environment. Rebuild shared clients and deploy matching API/outbox/worker v3
   code; never let an old worker acknowledge a search job it cannot execute.
3. Provision private Elasticsearch/authenticated runtime credentials using the
   [deployment guide](../phase-5-elasticsearch.md). Keep ES off public Nginx/ports;
   local HTTP override is explicit and is not production TLS certification.
4. Provision a dedicated operator database login/role, then use the documented CLI
   to create compatible generation/indexes. Never grant maintenance membership to
   the normal API/worker login. Supply the exact generated fingerprint consistently.
5. Enable compatible enrollment/transport/workers, run isolated smoke checks, then
   explicitly backfill historical current versions in bounded resumable batches.
   Ordinary startup never runs bulk historical backfill. Verify coverage before
   promoting/serving a generation; do not equate scheduled jobs with publication.
6. Enable keyword serving only after the real acceptance gates pass. Enable hybrid
   separately with compatible existing embedding profile/Qdrant ingestion. No
   automatic re-embedding/model download is required or performed for lexical work.

Use [all operator commands and cutover prerequisites](../phase-5-search-operations.md).
For the initial full generation, shadow build and verify before SQL cutover; this
selects SERVING explicitly. Do not manually edit ready pointers or generation rows.

## Configuration, security and limits

Existing validated `ELASTICSEARCH_*`, `SEARCH_ENROLLMENT_ENABLED`,
`SEARCH_GENERATION_FINGERPRINT`, `KEYWORD_SEARCH_*`, `HYBRID_SEARCH_ENABLED` and
private secret-file settings govern the deployment. See the
[environment reference](../deployment/environment-variables.md) and `.env.example`.
Default search flags remain off. Optional search downtime must not become a hard
CRUD readiness dependency. SQL reauthorization protects against stale index content.

Ownership is per stable internal user, not an implemented enterprise tenant model.
Queries/scopes/candidates/window/prefix/highlight/extraction limits are enforced.
Rebuild cutover supports at most 1000 eligible documents and a short SQL write fence;
larger corpora need further design/verification. No SQL/ES atomicity is claimed.
Full historical PDF viewing, exhaustive accessibility, universal model compatibility
and corpus-scale performance are not certified.

## Rollback and recovery

Disable search serving/enrollment to contain a search regression while preserving
catalog/storage and durable jobs. Do not downgrade the database by deleting search
rows, resetting volumes or rewriting historical migrations. Coordinate the worker/
relay versions so unsupported work remains durable, not falsely completed.

Retired generations are immutable; index rollback is a verified **forward rebuild**
into a fresh compatible generation. Keep previous physical data for investigation;
exact cleanup uses retained manifests and the 24-hour retirement/recheck policy.
Fingerprint-only older generated clients cannot safely manage multiple physical
generations after T10. See the operations guide for full rollback limitations.
