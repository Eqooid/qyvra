This patch adds native local adapters to the same v1.3.0 pipeline. It implements
no agents, tools, chat persistence, streaming, OCR, new formats or hybrid search.
Elasticsearch remains Planned. PostgreSQL owns originals' metadata, business state,
canonical text/chunks, profiles/checkpoints, durable jobs/outbox and index activation.
RabbitMQ transports identifiers, Redis accelerates disposable progress, and Qdrant
is derived/rebuildable. Original stored files stay in the storage abstraction.

## Actual provider boundaries and source navigation

- [Embedding contract](../../../apps/api/src/modules/ai/embedding-provider.ts):
  `embed({profile,purpose,inputs,signal})` returns validated ordered vectors with
  Qyvra input IDs. The [shared factory](../../../apps/api/src/infrastructure/embeddings/embedding-provider.factory.ts)
  dispatches the authoritative SQL profile's `provider`, not an HTTP request field.
- The existing OpenAI-compatible embedding adapter uses direct HTTP; the native
  Ollama adapter uses POST `/api/embed` plus before/after GET `/api/tags` digest checks.
  There is no OpenAI SDK baseURL setting; endpoint variables are full request URLs.
- [Generation contract](../../../apps/api/src/modules/ai/generation-provider.ts):
  bounded messages/signal → final content and optional token usage; independent
  [factory](../../../apps/api/src/infrastructure/generation/generation-provider.factory.ts).
  The compatible adapter uses chat-completions; native POST `/api/chat` supplies
  Qyvra JSON schema, no streaming/tools and a pinned tokenizer/framing contract.
- Worker module injects the embedding factory into durable generation jobs.
  Search module injects the same boundary for query vectors. RAG module injects
  the independent generation factory. Domain handlers do not select infrastructure SDKs.

The worker owns integrity → extraction → chunking → embeddings → vector indexing.
Each independently durable stage loads SQL/storage state, applies lifecycle/lease
fences, persists complete outputs and schedules the next stage through SQL/outbox.
There is no chained extraction/embedding call in the upload HTTP request.

The API owns user/session scope, compatible query embeddings, bounded Qdrant search,
SQL candidate hydration/reauthorization, bounded evidence, Qwen generation and
strict [citation validation](../../../apps/api/src/modules/ai/rag-citations.ts).
The UI receives the same provider-independent response and navigates to the exact
owned document/version/chunk via its existing source API. Index readiness is named
**READY** in this repository, not a new ACTIVE enum.

## Profiles, indexing and cutover

Fingerprint identity includes provider, model/revision, dimensions/distance, profile
version, normalization, tokenizer/version and query/document instructions. Different
models with the same dimensions are still incompatible. Native revisions pin the
installed model digest; bundle bytes also participate through tokenizerVersion.
No silent truncation/padding or profile-compatible fallback is provided.

Changing those embedding semantics requires a new immutable profile. Preserve old
checkpoints and collections. Schedule only necessary missing stages; chunk/profile
and transformed-input hashes fence checkpoint reuse. Collection/profile identity,
point IDs and SQL manifest generations keep vector spaces isolated. A BUILDING
replacement cannot serve until verified complete; SQL READY pointer publication
is authoritative. Stale/foreign payloads are never authoritative evidence.

Safe staged cutover:

1. Provision the new installed model and certified bundle/profile without mutating
   old profile records. Choose representative calibration and coverage requirements.
2. Move ingestion/worker profile/endpoint/assets together; generate new checkpoints
   and verified indexes through existing owned reprocessing or bounded backfill.
3. If the API still serves the old cloud profile, retain its matching cloud endpoint/key
   with a service-specific Compose override. Base Compose normally shares embedding
   transport settings, so changing a fingerprint alone is insufficient.
4. After verified coverage, explicitly switch SQL `AiServingProfile` and API
   fingerprint/endpoint/bundle together. Querying a mismatched configured/serving
   profile returns controlled unavailability, not a comparison of incompatible vectors.
5. Keep old valid artifacts until acceptance/rollback decisions. Use precise existing
   lifecycle cleanup; never delete a shared collection to force model switching.

Generation provider/model/endpoint changes do not create a new embedding profile,
invalidate checkpoints or require reindexing. Its model must independently satisfy
the structured-output/context contract and pinned framing.

## Native input/output correctness

Embeddings preserve input ordering and require exact result count, finite nonzero
vectors and configured dimensions. Native input and aggregate token limits are checked
before requests; Ollama truncation is disabled and actual token count must match.
Valid completed checkpoints are reused after bounded SQL retries. No bad vector or
partial batch becomes successful durable state.

Generation receives only authorized canonical excerpts with server-supplied source
tokens. Whole excerpts fit within tokenizer-based context/schema/reserve plus output
budget. Native responses must be complete, bounded and count-compatible; only final
content participates in strict parsing. Separate thinking is discarded. Models cannot
create authoritative URLs, document IDs, pages or chunk IDs. Unknown tokens/missing
citations/malformed JSON are rejected. No useful evidence skips inference or returns
the existing insufficient-evidence outcome; it never permits outside-knowledge answers.

## Security and reliable operations

Operator-configured URLs accept only validated HTTP(S), with no URL credentials,
query or fragment; private HTTP needs explicit opt-in. URL validation is not a
complete arbitrary-network SSRF defense: ordinary users cannot set these settings
and operators must protect DNS/network egress and sensitive provider hosts.
No provider route/key appears in the frontend or Nginx. Remote inference requires
protected private networking/TLS/authentication; unauthenticated LAN exposure is unsafe.

Current ownership uses stable authenticated `users.id`; there is no separate tenant
entity. Qdrant applies that user/profile scope, then SQL checks owned canonical tuple,
current version, lifecycle, complete chunk set and serving generation. Evidence is
checked again before publication; source navigation rechecks access. PDF text remains
untrusted JSON evidence, not system instructions. Models have no shell/FS/tool access.
Logs use IDs/counts/durations/categories, not full documents, vectors, secrets or raw
provider errors. Structural citations do not prove semantic truth or universal
prompt-injection resistance.

Connection/reset/timeout/408/429/5xx failures can be transient. Unknown model, bad
configuration/digest/schema/dimensions are deterministic failures; retries do not
repair them automatically. Embedding jobs reuse existing bounded SQL retry/backoff
and outbox recovery. Native generation is one bounded attempt; public errors remain
sanitized 503/504/429/502. Providers are not health-check inference dependencies.
Redis loss does not erase jobs/checkpoints; RabbitMQ interruption does not erase outbox intent.

Existing operator facilities:

- Owned processing status: `GET /api/v1/documents/{id}/versions/{versionId}/processing`.
- Owned reprocess: `POST /api/v1/documents/{id}/versions/{versionId}/ai/reprocess`,
  authenticated Origin/CSRF plus UUID Idempotency-Key and `{ "mode": "index" }` for
  derived-store rebuild. Other implemented modes: repair/extraction/chunking/embedding.
- Bounded backfill dry-run: `docker compose exec -T api node /app/infrastructure/docker/database-command.cjs node scripts/ai-backfill.cjs --batch 10 --max 100`.
  Inspect before using the existing `--apply` flag; resume with `--after` emitted cursor.

For Qdrant loss, rebuild compatible indexes from PostgreSQL vectors. T05 proved no
new embedding requests. Wait for replacement READY, not merely retained old readiness.
For a permanent failure, correct configuration/model/assets first and request intentional
reprocessing; do not fake final states, clear ownership filters or purge shared queues.
Archive/delete revokes evidence eligibility immediately even when cleanup is delayed.

### Embedding assumptions

The adapter supports batches and both purposes, but accepts only provider
`openai-compatible`, tokenizer `cl100k_base` and version `tiktoken-1.0.22`.
`qyvra-embedding-input/v1` prepends an optional purpose-specific instruction followed
by LF. It does not implement arbitrary local model task templates.

Requests contain model, input array, `encoding_format: float` and optional dimensions.
Responses must match the exact profile model string, input count/indices and vector
dimensions. Every vector must be finite and nonzero. The entire batch is validated
before checkpointing; no partial successful batch is recorded.

AbortSignal covers HTTP and bounded response reads. The durable worker owns the
deadline, retry schedule and recovery, not the adapter. Query embedding is bounded
by the search request deadline. SQL checkpoint hashes must represent exactly the
text actually embedded, including preprocessing; changing the adapter must not
leave hashing on an obsolete input transformation.

### Generation assumptions

Requests include system/user messages, temperature, configurable output-token field,
`stream: false`, `store: false` and `response_format` with strict JSON schema.
The adapter accepts exactly one choice with `finish_reason: stop`, nonempty bounded
content, no refusal and no tool calls. It does not support native Ollama envelopes.

The generation tokenizer is restricted to `cl100k_base` or `o200k_base`.
Context budgeting counts serialized messages/schema plus a 1,024-token reserve;
that is not verified accounting for Qwen chat templates or special tokens.
The current generation timeout ceiling is 60 seconds, RAG 120 seconds, search
60 seconds; embedding timeout is at most half the configured worker lease.
Defaults are generation 25 seconds, RAG 60 seconds and embedding 30 seconds with
a 120-second worker lease. CPU inference may exceed these bounds; measure first.

## API compatibility assessment

Ollama publishes a subset of OpenAI compatibility, including chat completions and
embeddings. The full URLs for the existing adapters would be
`http://<operator-selected-host>:11434/v1/embeddings` and
`http://<operator-selected-host>:11434/v1/chat/completions`, not just `/v1`.
Local Ollama does not require the SDK's dummy key because Qyvra uses HTTP directly.
[Ollama OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility).

Transport compatibility is plausible, but not a verified supported deployment.
Test the exact installed server's handling of schema strictness, `store`,
`max_tokens` versus `max_completion_tokens`, optional dimensions, model labels and
finish reasons. Choosing `GENERATION_OUTPUT_TOKEN_FIELD=max_tokens` can avoid one
compatibility concern; it does not correct tokenizer/context accounting or prove
grounded output quality. Unknown/unsupported fields must not silently defeat limits.

The existing compatible embedding request has no explicit no-truncation control.
Native `/api/embed` supports arrays, optional dimensions and `truncate: false`;
its documented default permits truncation. T01 has not established the installed
`/v1` route's behavior. Correct checkpoints require complete intended input, not
an unnoticed prefix. [Native embedding API](https://docs.ollama.com/api/embed).

Native `/api/chat` supports schema via `format`, non-streaming mode, thinking controls
and options. It returns a different envelope, requiring normalization into the
existing generation contract. Set `stream: false` explicitly; validate completion,
stop reason, content size and usage. Never expose a reasoning field as the answer.
[Native chat API](https://docs.ollama.com/api/chat).

| Approach                        | Complexity/maintenance                          | Fit and limitations                                                                                                            | Recommendation                                                                    |
| ------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Existing compatible HTTP only   | Lowest transport change                         | Needs local budgeting/preprocessing anyway; less explicit truncation/context/thinking control; exact feature parity unverified | Retain for existing deployments, not certify local models merely by changing URLs |
| Native Ollama only              | Two small adapters and protocol fixtures        | Explicit local controls; replacing compatible adapters would regress existing cloud configuration                              | Do not replace the existing adapters                                              |
| Both behind existing interfaces | Small provider factory plus two native adapters | Shared validation/checkpoint/citation contracts, independently selected providers; some additional tests                       | **Recommended, PLANNED**                                                          |

No AI framework or large SDK is necessary. Use native HTTP behind existing Qyvra
interfaces. ADR-006 is Proposed; implementation and model certification follow later.

## Local model assessment

Qwen chat models and Qwen embedding models are separate capabilities. Never use a
chat model as an embedding model just because its name contains Qwen.
Allow operator-selected generation tags, not a hardcoded single Qwen model.

Qwen-family generation candidates must demonstrate instruction following, schema
completion and source-token discipline under the existing RAG contract. Record
server version, model tag/digest, quantization, effective context and thinking mode.
Thinking behavior varies by model; models unable to honor the selected bounded
policy are not certified. CPU/GPU latency and quality require actual measurements.

| Embedding candidate            | Published expectation, not observed output                                  | Required validation                                                                         |
| ------------------------------ | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Original EmbeddingGemma        | 768-dimensional native output, optional reduced dimensions, 2K context      | Installed tag/revision, actual dimensions, document/query templates and tokenizer           |
| nomic-embed-text v1.5          | 768 native dimensions; upstream 8,192 context, Ollama listing advertises 2K | Effective server context and exact `search_document: ` / `search_query: ` prefixes          |
| Qwen3-Embedding 0.6B / 4B / 8B | 1,024 / 2,560 / 4,096 native dimensions; upstream 32K context               | Installed variants, reduced-dimension support, instruction template and actual input limits |

These are distinct identities, not defaults or a certified support matrix.
Google now also documents EmbeddingGemma 2; do not transfer its specifications to
the original tag. [Google specifications](https://ai.google.dev/gemma/docs/embeddinggemma),
[Nomic model card](https://huggingface.co/nomic-ai/nomic-embed-text-v1.5),
[Ollama Nomic listing](https://ollama.com/library/nomic-embed-text),
[Qwen3-Embedding specifications](https://github.com/QwenLM/Qwen3-Embedding).

Normalization and task instructions must follow the selected revision's requirements.
Qyvra's current instruction-plus-LF convention is not equivalent to every model's
inline prefix or task template. Where bytes change, use a new normalization version
and test matching query/document transformations and hashes. Never pad or truncate
vectors to force dimensions. Retain Cosine and validate nonzero finite vectors;
confirm any reduced-dimensional output/normalization against actual model behavior.

### Local token budgeting acceptance contract — PLANNED

Implement a small Qyvra-owned budgeting boundary supporting pinned, locally installed
tokenizer assets and chat templates. Determine the smallest compatible dependency
in T02/T03; T01 does not select an untested tokenizer package.
Require parity tests covering Unicode, special tokens, instructions, schema/template
overhead and effective input/output limits. Asset identity/version belongs in
embedding profile identity. Do not call OpenAI token counts Qwen token counts.
Do not fetch tokenizer/model assets or execute remote repository code on requests.

For embeddings, combine validated local budgets with `truncate: false`; reject
oversized input rather than persist vectors for incomplete text. For generation,
apply template-aware budgets, bounded native context/output options and completion
checks. Unknown tokenizer/model combinations fail closed. Conservative estimates
may support explicitly experimental testing, but do not certify a model's exact
context compliance. Thinking must be bounded or disabled for supported models.

## Profile, checkpoint and index compatibility

The existing fingerprint includes profile version, provider, model/revision,
dimensions, distance, normalization, tokenizer/version and both purpose instructions.
Endpoint, key, timeout and batch size are operational settings outside that identity.
Existing SQL storage can represent a new provider string without inventing another
profile entity. No schema migration is expected solely for native Ollama support.

Use a new immutable profile with planned provider `ollama`, exact model revision or
digest and validated local preprocessing/tokenizer identity. A model alias is not
immutable; checking a returned model label does not pin weights. Provisioning must
record/verify operator-installed revision, reject drift and require a new profile
when compatibility-relevant assets, dimensions or preprocessing change.

Never reuse an OpenAI checkpoint for a different local profile. The shared handler
must validate transformed-input hashes and dimensions before reuse. Preserve full
batch validation, live leases, current-run/lifecycle checks and PostgreSQL retries.
Provider selection should dispatch from the authoritative request profile; worker
and query paths must use the same selection rules.

Qdrant collections are profile-specific (`qyvra_chunks_<profile UUID without hyphens>_v1`),
with declared dimensions/Cosine and manifest-scoped point identities. PostgreSQL
manifests and `VersionReadyIndex`, not payload flags, determine publication.
Different models/providers/dimensions require separate compatible vectors/indexes.

Operator migration, later implementation only:

1. Provision and validate the new immutable local profile and model/tokenizer assets.
2. Configure the worker for the replacement profile; reuse valid extraction/chunks.
3. Generate new embeddings and a verified replacement index; activate through SQL.
4. Switch `AiServingProfile` and API serving fingerprint after intended corpus coverage.
5. Clean obsolete generations through existing durable cleanup, retaining required history.

An existing same-profile READY generation can serve during a replacement build.
A cross-profile rollout needs an explicit serving cutover; this is not automatic
multi-profile search. Qdrant loss alone must rebuild from valid SQL embeddings
without invoking the embedding provider. No reindex or profile creation occurs in T01.

## Deployment, hardware and security

`localhost` inside API/worker containers identifies that container. Both services
have the default bridge for provider egress plus the internal vector network.
Qdrant has only the private vector network. There is currently no Ollama service,
GPU reservation, host alias or provider route through Nginx.

| Inference location                  | Operator endpoint design                                                                                         |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Host development without containers | localhost is appropriate when API/worker and Ollama share the host                                               |
| Docker Desktop host                 | Operator-selected `host.docker.internal`; ensure Ollama listens on an interface reachable from containers        |
| Native Linux host                   | Optional explicit host-gateway alias in an override, or reachable host address; do not hardcode across platforms |
| Optional Compose service            | Private service DNS on a shared egress/provider network; optional profile, not mandatory app dependency          |
| Trusted LAN/dedicated AI server     | Private DNS/IP reachable by API and worker; firewall and authenticated TLS proxy where appropriate               |

[Docker Desktop networking](https://docs.docker.com/desktop/features/networking/)
describes the host alias. `OLLAMA_HOST` is an Ollama-server setting, not a current
Qyvra environment variable. Do not automatically add Ollama or publish port 11434.

Qyvra uses HTTP irrespective of CPU, NVIDIA or AMD deployment. CPU-only is allowed;
GPU drivers/toolkits, ROCm/backend compatibility and device passthrough are operator
responsibilities. AMD Radeon support depends on the actual model/platform matrix,
not all cards; no GPU is required. [Ollama hardware support](https://docs.ollama.com/gpu).
Model weights, quantization, KV cache, context and concurrency affect RAM/VRAM.
Measure cold/warm load, embedding throughput and RAG latency; no fixed SLA is promised.
Do not blindly increase timeouts or workers: keep lease safety and bounded admission.

Endpoints are trusted server-side operator configuration, never request/browser
parameters. Existing URL checks reject credentials/query/fragment and require HTTPS
or explicit HTTP; fetch rejects redirects. These checks are not a destination
allowlist or DNS-rebinding defense. Protect configuration, asset paths and network
egress; do not expose arbitrary user-controlled URLs. Local unauthenticated Ollama
must remain private. Remote deployments need segmentation, TLS/authentication proxy
as appropriate. No browser Ollama connection/CORS configuration is needed.

Authorized document text is sensitive even when sent locally. Review operator trust,
provider retention and proxy logs. Keys stay outside profiles, prompts, vectors,
RabbitMQ and frontend. Log categories/duration/model identities, not prompts,
response bodies, authorization headers or secrets. No second tenant/authorization
model is introduced: the current application uses trusted internal user ownership;
future tenant support must derive from the authoritative access model.

## Failure, recovery and RAG behavior

Existing embedding HTTP 429/408/5xx and network/timeouts are retryable; other HTTP
4xx and invalid output are permanent, with sanitized categories and bounded
Retry-After. Unknown-model semantics need native fixture/live validation; classify
from observed status/meaning, not a speculative string match.
Native adapters should map temporary outages/model loading/resource failures to
bounded existing retry categories and unknown model, unsupported operation,
dimension/config errors and invalid response to deterministic failures as appropriate.
Preserve the one-attempt adapter and PostgreSQL retry authority.

Generation currently distinguishes timeout/rate limit/unavailable/invalid output;
other HTTP failures are coarse unavailable. Interactive RAG is not a durable job
and has no automatic background generation retries. Native failures must retain safe
API errors rather than leak provider bodies. Local loading delays do not justify
false completion, partially checkpointed batches or rerunning valid embeddings.

RAG must retain authorized retrieval and reauthorization before context and response,
request-local source tokens, strict claims schema and server-derived citations.
Unknown tokens, malformed JSON, missing citations, refusal/tool output or incomplete
generation fail closed. Insufficient evidence remains a valid explicit outcome;
when retrieval provides none, avoid unnecessary generation as currently designed.
Document injection remains untrusted evidence. Schema/provenance validation cannot
prove every cited claim is factually entailed; model quality remains a measured risk.
Do not weaken validation to accommodate a local model or expose reasoning as content.
