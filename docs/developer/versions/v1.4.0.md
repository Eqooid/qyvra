Upload/version/metadata operations enroll through existing SQL transaction hooks.
Jobs and outbox records commit with lifecycle revisions. The relay publishes compact
v3 identifiers, workers validate/lease/fence and read immutable storage through the
existing abstraction. Lexical extraction shares canonical artifacts with AI without
calling a model. Workers persist deterministic cleanup manifests, write/verify ES,
then finalize under authoritative SQL guards. No network call belongs in a SQL
transaction; index writes can survive a rolled-back SQL publication.

Search first derives bounded authorized current-version scopes, then asks ES and,
for hybrid, existing profile-compatible semantic retrieval for candidates. RRF60
combines document ranks, not raw scores. A final SQL snapshot reauthorizes and
constructs canonical output. Redis windows contain identities/ranks and context
bindings, never raw queries/snippets or cached authorization. Every continuation
rehydrates; later revocation may leave rank gaps or an empty page.

## HTTP and frontend contracts

- `POST /api/v1/search/keyword`: literal terms/phrase, independent of models.
- `POST /api/v1/search/hybrid`: both legs required, explicit 503/504 on failure.
- Existing semantic-only endpoint/AI Search remain unchanged.
- `POST /api/v1/search/suggestions`: authenticated bounded authorized metadata
  prefixes, no global vocabulary or extracted-body terms.
- `GET /api/v1/documents/:documentId/versions/:versionId/extractions/:extractionId/pages/:pageNumber/segments/:segment`:
  exact canonical historical text, reauthorized for every read.

Use [API conventions](../../api.md), [keyword contracts](../../phase-5-keyword-search.md),
[hybrid windows](../../phase-5-hybrid-search.md) and
[evidence contracts](../../phase-5-search-evidence.md) for full DTOs/examples/errors.
Page numbers are one-based; segment numbers zero-based; highlight offsets are
Unicode scalar, half-open positions, not JS UTF-16 indices. No raw DSL/index selector
or storage URL is accepted. Public counts describe owned SQL coverage, not private
engine hit totals.

The protected `/search` page reuses AuthApi, TanStack ownership context and shadcn.
It supports Keyword/Hybrid, a subset of backend filters, keyboard autocomplete,
bounded fixed pages and safely rendered React highlights. A Sheet opens exact
text/page segments; it is not a binary historical PDF viewer. Back restores only
owner-scoped form drafts; private queries and results are not persisted in URLs or
browser storage. Session changes clear private state. See the
[frontend behavior and accessibility limits](../../phase-5-search-frontend.md).

## Local setup and operations

Follow existing [getting started](../../development/getting-started.md) and
[private ES provisioning](../../phase-5-elasticsearch.md), rather than creating a
new network or search client. Use Node 24 and existing per-package lockfiles.
Database/client/API/worker builds must match the applied migrations. Search flags
default off. Optional `docker-compose.search.yml` requires private secret files;
debug host access uses only the explicit loopback override. Nginx never proxies ES.

The [operator guide](../../phase-5-search-operations.md) owns exact setup commands,
generation fingerprints, role provisioning, dry-run/apply, durable operation IDs,
checkpoints, cancellation, cutover, cleanup and troubleshooting. No bulk work runs
automatically at startup. Never reset storage or reuse production indexes in tests.
No new provider/model or re-embedding is needed for lexical operations.

Common failures: disabled/mismatched enrollment or serving flags, incompatible index
schema, unavailable search engine, unsupported/textless PDF, expired cursor, wrong
embedding profile, active maintenance lease or unready shadow. Inspect durable SQL
job/operation error categories; never log query text, PDF content or credentials.
Keyword does not silently fall back to database substring search; Hybrid does not
silently become Keyword. Use explicit mode selection and fresh cursors.

## Verification commands and evidence

From the relevant application/package, use existing `lint`, `typecheck`, `build`,
`test`, `test:integration`, `test:e2e` and format scripts. The exact selected commands,
known full-format failure, prior full-suite evidence and infrastructure requirements
are in [T11 verification](../../phase-5-verification.md#t11-commands-and-results).
Full frontend format is not currently green; do not report scoped formatting as
equivalent. Avoid rerunning costly unchanged suites without invalidating changes.

`node node_modules/@playwright/test/cli.js test --config playwright.search.config.ts`
from `apps/web` starts the production server and runs real Chromium with **mocked
API responses** after `npm run build`. It proves UI interactions, not Nginx/indexing.
The separate live `phase-five-search.spec.ts` needs an isolated configured Nginx
stack and `E2E_SEARCH_ENABLED=true`/approved project-name guards. Real adapter and
maintenance checks use `node infrastructure/test/search-runtime.cjs` from the root
with a disposable migrated `TEST_DATABASE_URL`. Those tests are not safe commands
for production data and do not replace broker/model/quality gates.

CI uses Node 24 and locked installs; the Phase 4 workflow preserves existing
regressions. Phase 5 adds private search/maintenance and mocked-browser jobs.
T11 parsed the updated workflow and exercised affected local commands, but no
reviewed-candidate remote CI pass or Linux image build is claimed. Consult the
acceptance matrix before changing the version or preparing a release.
